## 0) خريطة الوضع الحالي (Landscape)

بعد تحليل مباشر للكود الفعلي (لا افتراضات)، الصورة الحقيقية هي **ثلاثة أنظمة** لا واحد:

| # | النظام | التقنية | الحالة | الموقع المحلي |
|---|--------|---------|--------|----------------|
| **A** | **البرودكشن** — ABC Ticketing | Django 5.0.9 + DRF + Channels + PostgreSQL + CRA | **حيّ ويخدم المستشفى** (`:8000` / `:3000`) | `abc-production/` |
| **B** | **نظام PR** — رضا المرضى والزوار | Express 4 + TS + React 19 + PostgreSQL | مستقل، مُصلَح حديثاً | `abc-pr/` |
| **C** | **النظام الجديد** — ABCH Ticketing CRM | NestJS + Prisma + React 19 + Redis | قيد التطوير (dev) | جذر المشروع |

> **ملاحظة استراتيجية جوهرية:** النظامان A وC يفعلان **نفس الشيء** (إدارة تذاكر) بتقنيتين مختلفتين. الاستمرار في تطوير الاثنين معاً يضاعف التكلفة والصيانة. القرار المعتمد حالياً هو تطوير A داخل Django مع بناء C كمنتج SaaS — وهذا مقبول **بشرط** تحديد أفق زمني لدمجهما (راجع §4).

## 2) المسار A — إكمال وإصلاح نظام البرودكشن (Django)

**القرار المعتمد:** الإبقاء على Django + CRA بنفس الهيكل والتصميم، وإعادة بناء مميزات النظام الجديد بداخله.

### المرحلة A0 — الطوارئ الأمنية (أسبوع)
- [ ] تدوير الاعتمادات الخمسة ونقلها لمتغيّرات بيئة.
- [ ] `DEBUG=False` + `ALLOWED_HOSTS` + CORS allowlist + إغلاق Swagger + تفعيل HSTS/SSL.
- [ ] إصلاح IDOR في تعليقات التذاكر + مراجعة كل `ViewSet` بلا `permission_classes`.
- [ ] `verify=True` للطلبات الصادرة.

### المرحلة A1 — تنظيف وتثبيت (2–3 أسابيع)
- [ ] **حذف التطبيقات الميتة**: `tickets/` و`dashboards/` (1,811 سطر ≈ ثلث كود Python) — بعد التأكد من عدم وجود صفوف `django_migrations` لها.
- [ ] إصلاح **تسريب thread-local** (`middlewares.py:10` معامل افتراضي قابل للتغيير) — قد يخلط طلبات المستخدمين.
- [ ] إصلاح انهيار `Department.modules = NULL` (يسبب 500 في كل صلاحيات `ticket` و`pr`).
- [ ] إصلاح `post_save` العودي + `Ticket.save()` الذي يبتلع `*args/**kwargs`.
- [ ] إصلاح الإشعار المزدوج (FCM يُرسَل مرتين).
- [ ] إصلاح التواريخ الساذجة (naive datetime) — كل تقارير المدى الزمني مُزاحة بفارق توقيت القاهرة.
- [ ] إصلاح `custom_exception_handler` (يحوّل 400 إلى 500 مع قوائم الأخطاء).
- [ ] تثبيت الاعتماديات (لا يوجد lockfile؛ `channels==3.0.0` يتعارض مع `daphne` 4.x).

### المرحلة A2 — البنية التحتية (2–3 أسابيع)
- [ ] **`InMemoryChannelLayer` → Redis**: الوقت الفعلي **معطّل فعلياً عند أكثر من عملية واحدة** (Redis مثبّت ويعمل أصلاً).
- [ ] **استبدال `threading.Thread` بـCelery** (المكتبة مثبّتة وغير مُستخدمة): التصدير والإشعارات تموت مع إعادة التشغيل وبلا إعادة محاولة.
- [ ] تفعيل تخزين مؤقت صحيح (`FetchFromCacheMiddleware` مفقود → الكاش يُكتب ولا يُقرأ).
- [ ] تحديد سقف للتصدير (يحمّل كل التذاكر في الذاكرة).
- [ ] **تحديد مصدر الواجهة الحيّة**: النسخة المُنزَّلة **لا تطابق الباك-إند** (تشير لنطاق `support.csch-svu.com` ومسارات API قديمة) — يجب تأكيد أي نسخة تعمل فعلاً قبل اعتبارها المرجع.

### المرحلة A3 — إضافة مميزات النظام الجديد (6–10 أسابيع)
نطاق التذاكر الحالي **بسيط**: 4 حالات فقط (`on_hold → in_progress → complete → closed`)، **بلا أولوية، بلا مُسنَد إليه، بلا SLA**، والتوجيه على مستوى القسم فقط.

| الميزة | الحالة في البرودكشن | العمل المطلوب |
|--------|---------------------|----------------|
| **SLA + تنبيهات الخرق** | ❌ غير موجود | نموذج SLA لكل قسم/نوع + مهام Celery دورية |
| **الأولويات** | ❌ | حقل + فهرسة + فرز |
| **الإسناد لموظف** | ❌ (قسم فقط) | FK + إشعارات + KPI |
| **RBAC حقيقي** | ❌ (أدوار مُشتقّة من `department is null` و`is_superuser`) | جداول أدوار/صلاحيات + ترحيل |
| **قاعدة المعرفة** | ❌ | تطبيق جديد |
| **ساحة الفريق** | ❌ | تطبيق جديد |
| **الأصول** | ❌ | تطبيق جديد |
| **سجل تدقيق شامل** | جزئي (`simple-history` على التذاكر فقط) | توسيع + IP/UserAgent |
| **تحليلات متقدمة** | جزئي (pandas في الطلب) | استعلامات مُحسّنة + كاش |
| **إدارة المستخدمين من الواجهة** | ❌ (Django admin فقط) | شاشات إدارة |

### المرحلة A4 — الجودة (مستمر)
- [ ] **تغطية اختبارات صفر حالياً** (ملفات `tests/__init__.py` فارغة) → بناء مجموعة اختبارات من الصفر.
- [ ] CI/CD + linting + تثبيت إصدار Python (3.10+ مطلوب لـDjango 5).
- [ ] إصلاح الترجمة: `LOCALE_PATHS` يشير لمجلد غير موجود → **كل نصوص `gettext` تظهر بالإنجليزية** رغم `LANGUAGE_CODE='ar'`.

## 4) المسار C — النظام الجديد إلى SaaS

الخطة التفصيلية موثّقة في [`خطة-تطوير-المنصة.pdf`](خطة-تطوير-المنصة.pdf) (11 صفحة). ملخّص المراحل:

| المرحلة | المحتوى | المدة |
|---------|---------|-------|
| 0 | تثبيت وأمان | أسبوعان |
| 1 | Multi-Tenancy + RLS | 4–6 أسابيع |
| 2 | امتثال صحي (تشفير/تدقيق/تخزين آمن) | 4–6 أسابيع |
| 3 | طبقة SaaS (تسويق/تسجيل/فوترة) | 4–6 أسابيع |
| 4 | جودة ومراقبة | مستمر |
| 5 | إطلاق | 2–3 أسابيع |

### ما أُنجز فعلياً ✅
النظام **يعمل محلياً بالكامل** بعد اكتشاف وإصلاح **9 أخطاء حاجبة** (لم يكن قد شُغِّل end-to-end من قبل):
1. `UploadsModule` بلا `PrismaModule` → الباك-إند لا يقلع.
2. CSRF مكسور (الكود يكتب فوق كوكي المكتبة) → كل تسجيل دخول يفشل.
3. `useLogin` بلا `credentials` وبلا هيدر CSRF.
4. CORS يحجب هيدر `x-csrf-token`.
5. + 6. تعريف مكرّر لـ`error` في صفحتَي الأدمن → خطأ تصريف.
7. نسختان من Zustand store (استيراد بلا `.ts`) → الدخول ينجح والتطبيق لا يراه.
8. `TicketStatus` enum ناقص `open` → التحليلات ترجع 400.
9. انهيار منهجي في كل صفحات القوائم (`{data}` مقابل مصفوفة) — أُصلح مركزياً بـ`asList()`.
+ إضافة `ErrorBoundary`. **تحقّق: كل الـ18 مسار تُعرض بلا انهيار.**
