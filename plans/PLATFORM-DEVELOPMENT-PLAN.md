## 0) الملخص التنفيذي (Executive Summary)

المنصة الحالية **نظام تذاكر/دعم داخلي ناضج تقنياً** مبني على NestJS + React 19 + PostgreSQL، مصمّم لمؤسسة واحدة (مستشفى ABCH). البنية سليمة، والأمان المحيطي جيد، والميزات غنية (دورة حياة تذاكر متقدمة، SLA، RBAC ثلاثي الطبقات، تحليلات، قاعدة معرفة، Real-time).

**لكن ليتحوّل إلى منتج SaaS احترافي يُسوَّق لعدة مستشفيات ومؤسسات، تنقصه ثلاث ركائز غير موجودة اليوم:**

1. **عزل المؤسسات (Multi-Tenancy):** المنصة أحادية المستأجر بالكامل — لا يوجد مفهوم "مؤسسة/مستشفى" في قاعدة البيانات.
2. **الامتثال الصحي (Healthcare Compliance):** لا يوجد تشفير للبيانات الحساسة، ولا سجل تدقيق محكم، ولا سياسات احتفاظ بالبيانات — وهي متطلبات إلزامية للمستشفيات.
3. **طبقة المنتج التجاري (SaaS Layer):** لا توجد صفحة تسويقية، ولا تسجيل ذاتي، ولا اشتراكات/فوترة، ولا إدارة حسابات مؤسسية.

**القرار الاستراتيجي (مُتّفق عليه):** نبني على NestJS الحالي (لا نعيد الكتابة) → نحوّله إلى **SaaS متعدد المؤسسات** → مع **امتثال صحي كامل (HIPAA-grade)** → ثم طبقة تسويق ومنتج.

**المدة التقديرية للوصول لأول عميل مستشفى قابل للبيع:** 4–6 أشهر بفريق مركّز (التفصيل في §8).

## 1) تقييم الوضع الحالي (Current State Assessment)

### 1.1 نقاط القوة (نبني عليها — لا نلمسها)

| المجال | التقييم |
|--------|---------|
| **المعمارية** | NestJS modular نظيف، فصل واضح للمسؤوليات، Prisma بفهرسة مدروسة |
| **دورة حياة التذكرة** | آلة حالات (state machine) موثّقة تفرض تأكيد المُنشئ قبل الإغلاق — من أفضل ما في الكود |
| **الأمان المحيطي** | JWT fail-fast، bcrypt cost 12، قفل الحساب (5 محاولات/15 دقيقة)، Helmet + CSP + HSTS، CORS allowlist، CSRF double-submit، Throttler بـ6 طبقات |
| **رفع الملفات** | فحص الامتداد + MIME + magic-byte + منع path-traversal + حد 5MB |
| **Real-time** | Socket.IO مع Redis adapter، إدارة اتصال صحيحة، rate limiting لكل حدث |
| **RBAC** | 3 طبقات: دور المستخدم → صلاحيات القسم → تجاوزات لكل مستخدم |
| **الواجهة** | تصميم متماسك، Dark mode، ثنائي اللغة AR/EN + RTL، responsive، React Query |
| **التوثيق** | توثيق ضخم (54 endpoint، ER diagram، أدلة أدوار) |

### 1.2 الفجوات الحرجة (Blocking Gaps)

مرتّبة حسب الأثر على هدف "SaaS احترافي للمستشفيات":

**أ) معمارية (Architecture)**
- ❌ **أحادي المستأجر بالكامل** — لا `Organization`/`Tenant`، العزل بالكود على مستوى القسم فقط.
- ❌ **لا Row-Level Security** — لا حماية على مستوى قاعدة البيانات ضد تسرّب بيانات بين المؤسسات.
- ⚠️ **توجيه الواجهة يدوي** — `App.tsx` يستخدم `useState`+CustomEvents بدل `react-router-dom` (مثبّت لكنه غير مُستخدم) → لا روابط عميقة ولا حماية مسارات حقيقية.

**ب) الامتثال الصحي (Healthcare / HIPAA)**
- ❌ **لا تشفير للبيانات الحساسة (PHI/PII)** — الأسماء والهواتف والملاحظات مخزّنة نصاً صريحاً.
- ⚠️ **سجل التدقيق غير مكتمل** — أعمدة `ipAddress`/`userAgent` موجودة لكن لا تُملأ أبداً؛ الكتابة يدوية ومتناثرة وغير محكمة (tamper-evident).
- ❌ **لا سياسات احتفاظ/حذف بيانات، لا نسخ احتياطي/DR في الريبو، لا فحص فيروسات للملفات المرفوعة.**
- ❌ **تخزين الملفات محلي غير مشفّر** — لا S3/object storage، مشكلة كبيرة لبيانات المرضى.

**ج) الأمان (Security — أولوية فورية)**
- ❌ **الخروج (Logout) لا يُبطل التوكن** — refresh token صالح 7 أيام حتى بعد الخروج، لا blacklist ولا rotation.
- ❌ **التحقق من المدخلات (Validation) على endpoint واحد فقط من ~54** — الباقي `body: any`.
- ⚠️ **أسرار مكتوبة في `docker-compose.yml`** (كلمة مرور DB + أسرار JWT) — مُودعة في git.
- ⚠️ **تسريب صلاحيات في `getDepartmentPerformance()`** — المشرف يرى كل الأقسام (تجاهل الدالة لمعاملاتها).
- ❌ **لا endpoint لتغيير/استرجاع كلمة المرور ذاتياً** — رغم وجود flag `forcePasswordChange`.

**د) المنتج التجاري (Productization)**
- ❌ لا صفحة هبوط/تسويق، لا تسجيل ذاتي، لا onboarding.
- ❌ لا اشتراكات/فوترة/خطط، لا إدارة حساب مؤسسي.
- ❌ لا بريد إلكتروني/SMS (إشعارات push فقط) — ضروري لتنبيهات SLA والاسترجاع.

**هـ) الجودة (Quality)**
- ❌ **صفر اختبارات فعلية** (backend وfrontend) رغم تهيئة Vitest كاملة.
- ⚠️ **`any` منتشر** (~146 backend، ~107 frontend) + `strict: false` → أمان أنواع ضعيف.
- ⚠️ لا CI/CD، لا ESLint/Prettier (الـ`lint` مجرد `tsc --noEmit`).
- ⚠️ لا logging مُهيكل، لا metrics/APM، health check بدائي (لا Redis/queue).
- ⚠️ ملف React (`NotificationProvider.tsx`) في غير موضعه داخل مجلد الباك-إند (كود ميت).

## 2) التوجّه الاستراتيجي (Strategic Direction)

بناءً على القرارات المتّفق عليها:

| البُعد | القرار | الأثر |
|--------|--------|-------|
| **نموذج التشغيل** | **SaaS متعدد المؤسسات (Multi-Tenant)** | نشر واحد يخدم كل المستشفيات مع عزل كامل — الأمثل للتسويق والتوسّع |
| **الامتثال** | **كامل (HIPAA-grade)** | تشفير + تدقيق محكم + احتفاظ + ضوابط وصول — يفتح باب المستشفيات الكبيرة والحكومية |
| **اللغة/التقنية** | **الإبقاء على NestJS + React** | لا إعادة كتابة — البناء على الأصول الموجودة |
| **الأولوية** | **خطة + بدء فوري بالإصلاحات الحرجة** | مسارات متوازية: إصلاح أمني الآن + تحوّل معماري بالتوازي |

**نموذج العزل المُختار (Tenancy Model):** **Shared Database, Shared Schema + `tenantId` + Row-Level Security (RLS)**.
- لماذا؟ أفضل توازن بين التكلفة التشغيلية والعزل. كل جدول قابل للعزل يحمل `tenantId`، وPostgreSQL RLS يفرض العزل على مستوى القاعدة (دفاع ثانٍ بعد الكود)، مع خيار ترقية العملاء الكبار (Enterprise) إلى schema/DB منفصل لاحقاً.

## 3) خارطة الطريق — المراحل (Roadmap)

> المراحل متوازية جزئياً. المرحلة 0 (أمان) تبدأ **فوراً** بالتوازي مع 1 و2.

### المرحلة 0 — التثبيت والأمان الفوري (Stabilize & Secure) — أسبوعان
**الهدف:** إغلاق الثغرات الأمنية الحرجة وتأسيس الجودة قبل أي توسّع.

- [ ] التحقق الفعلي من الـbuild والاختبارات (خط أساس).
- [ ] إخراج الأسرار من `docker-compose.yml` إلى `.env` + إنشاء `.env.example` + توثيق تدوير الأسرار.
- [ ] **إبطال refresh token** عند الخروج (Redis blacklist + token rotation + `jti`).
- [ ] عدم إرجاع refresh token في جسم الاستجابة (cookie httpOnly فقط).
- [ ] **تطبيق Zod validation** على كل الـmutation endpoints (أولوية: تغيير كلمة المرور، إنشاء مستخدم، الأصول، العمليات الجماعية).
- [ ] **تغيير/استرجاع كلمة المرور ذاتياً** (endpoint + واجهة) + تفعيل `forcePasswordChange`.
- [ ] إصلاح تسريب صلاحيات `getDepartmentPerformance()`.
- [ ] **التقاط IP/UserAgent** في كل كتابات سجل التدقيق (interceptor).
- [ ] إعداد **CI/CD** (GitHub Actions: lint + test + build gates) + **ESLint/Prettier**.
- [ ] تفعيل `tsconfig strict` تدريجياً + حذف الكود الميت (`NotificationProvider.tsx` من الباك-إند).

### المرحلة 1 — التحوّل متعدد المؤسسات (Multi-Tenancy) — 4–6 أسابيع
**الهدف:** كل مؤسسة معزولة تماماً؛ نشر واحد يخدم الجميع.

- [ ] نموذج `Organization` (المستشفى) + `OrganizationMembership` + خطة/حالة الاشتراك.
- [ ] إضافة `tenantId` (organizationId) لكل الجداول القابلة للعزل + Migration + backfill للبيانات الحالية.
- [ ] **حلّ المستأجر (Tenant Resolution):** subdomain (`hospital-a.app.com`) و/أو claim في JWT.
- [ ] **Prisma middleware/extension** يحقن `tenantId` تلقائياً في كل استعلام (منع التسرّب برمجياً).
- [ ] **PostgreSQL Row-Level Security (RLS)** كطبقة دفاع ثانية على مستوى القاعدة.
- [ ] فصل الأدوار: **Platform Super Admin** (مالك المنصة) مقابل **Tenant Admin** (أدمن المستشفى).
- [ ] **Tenant onboarding**: إنشاء مؤسسة جديدة، أول أدمن، البيانات الأولية (seed) لكل مؤسسة.
- [ ] عزل التخزين والملفات والإشعارات وSocket rooms حسب المؤسسة.
- [ ] اختبارات عزل صارمة (tenant isolation tests) — لا يرى أي مستأجر بيانات مستأجر آخر.

### المرحلة 2 — الامتثال الصحي (Healthcare & HIPAA) — 4–6 أسابيع
**الهدف:** جاهزية للتعامل مع بيانات المستشفيات ومعلومات المرضى.

- [ ] **تشفير الحقول الحساسة (Field-level encryption)** للـPHI/PII (أسماء، هواتف، ملاحظات) — at rest.
- [ ] **سجل تدقيق محكم (tamper-evident audit)**: كتابة موحّدة عبر interceptor، append-only، تسلسل/توقيع (hash-chain)، مع IP/UserAgent/tenant.
- [ ] **سياسات الاحتفاظ والحذف** (data retention & right-to-erasure) + مهام cron للتطهير.
- [ ] **انتهاء الجلسة بالخمول (session/idle timeout)** + إعادة مصادقة للعمليات الحساسة.
- [ ] **تخزين ملفات آمن**: S3/MinIO مع تشفير + توقيع URLs + **فحص فيروسات (ClamAV)**.
- [ ] **النسخ الاحتياطي وDR**: نسخ آلي مشفّر + خطة استعادة موثّقة + اختبار استعادة دوري.
- [ ] **ميزات القطاع الصحي**: تصنيفات/أولويات طبية (طوارئ/عيادات/أجهزة طبية/IT حيوي)، حقول مخصّصة، قوالب تذاكر طبية.
- [ ] (اختياري متقدم) **خطاف تكامل HL7/FHIR** للربط مع أنظمة المستشفى (HIS/EMR) — واجهة قابلة للتوسّع.
- [ ] وثيقة الامتثال (Security & Compliance Whitepaper) + قائمة ضوابط HIPAA + جاهزية BAA.

### المرحلة 3 — طبقة المنتج التجاري (SaaS Productization) — 4–6 أسابيع
**الهدف:** من "أداة داخلية" إلى "منتج يُشترى ويُشترك فيه".

- [ ] **إعادة بناء التوجيه** بـ`react-router-dom` (روابط حقيقية، deep links، حماية مسارات، back/forward).
- [ ] **صفحة هبوط/تسويق احترافية** (عامة، ثنائية اللغة) — القيمة، الميزات، القطاع الصحي، دعوة للتجربة.
- [ ] **التسجيل الذاتي + Onboarding**: إنشاء مؤسسة، تأكيد بريد، معالج البدء الأول، بيانات تجريبية.
- [ ] **الفوترة والاشتراكات** (Stripe/Paddle): خطط/طبقات، حدود الاستخدام، فترة تجريبية، فواتير.
- [ ] **إدارة الحساب المؤسسي**: إعدادات المؤسسة، الأعضاء والدعوات، العلامة التجارية (white-label/theming لكل مؤسسة).
- [ ] **البريد وSMS** (SendGrid/SES + Twilio): تأكيد، استرجاع كلمة مرور، تنبيهات SLA، ملخصات.
- [ ] **بوابة الطلبات العامة (اختياري)**: نموذج تقديم تذكرة عام للموظفين/الزوار دون تسجيل دخول كامل.

### المرحلة 4 — الجودة والمراقبة (Quality, Testing & Observability) — مستمرة/بالتوازي
- [ ] **مجموعة اختبارات**: backend (unit + integration + tenant-isolation)، frontend (components + pages)، E2E (Playwright).
- [ ] رفع تغطية الاختبارات تدريجياً نحو 80% + فرضها في CI.
- [ ] **Logging مُهيكل (pino/JSON)** + correlation IDs + tenant context.
- [ ] **Metrics + APM** (OpenTelemetry — الحزمة مثبّتة لكن غير موصولة) + لوحات مراقبة.
- [ ] **Health checks** liveness/readiness + Redis/queue + تنبيهات.
- [ ] **الأداء**: caching للتحليلات، حل N+1، حدود pagination، فهارس.
- [ ] **الوصولية (Accessibility/WCAG)**: ARIA، تسميات، تباين — شرط في مناقصات المؤسسات.
- [ ] تنظيف الدين التقني: تقسيم `tickets.service.ts` (1000+ سطر)، إزالة `any`، توحيد استراتيجية التحقق.

### المرحلة 5 — التمكين التسويقي والإطلاق (Go-To-Market) — 2–3 أسابيع
- [ ] **بيئة عرض/تجربة (Demo/Sandbox)** ببيانات مستشفى واقعية.
- [ ] **مواد تسويقية**: عروض، دراسات حالة، ورقة أمان، مقارنة مع المنافسين.
- [ ] **بنية تحتية سحابية (IaC)** + نشر إنتاجي + مراقبة + SLA/uptime.
- [ ] **توثيق العميل**: أدلة، فيديوهات، مركز مساعدة.
- [ ] **قياس النجاح**: تفعيل، احتفاظ، وقت الحل، رضا العملاء (CSAT).

## 6) نموذج البيانات — تغييرات رئيسية (Data Model Changes)

- **جديد:** `Organization`, `OrganizationMembership`, `Subscription`/`Plan`, `Invitation`, `EmailVerification`, `PasswordReset`, `RefreshTokenBlacklist` (أو `Session`).
- **تعديل:** إضافة `organizationId` لكل الجداول القابلة للعزل (Ticket, User, Department, Building, Floor, Asset, KnowledgeArticle, TeamNote, AuditLog, ...).
- **تشفير:** حقول PHI/PII عبر Prisma middleware للتشفير/فك التشفير الشفّاف.
- **تدقيق:** `AuditLog` → append-only + hash-chain + ملء IP/UserAgent/organizationId دائماً.

- **تجاري:** أول مستشفى تجريبي (pilot)، ثم أول عميل مدفوع، معدل تفعيل، CSAT.

## 10) الخطوة التالية الفورية

1. اعتماد هذه الخطة وترتيب الأولويات.
2. البدء بالمرحلة 0 (الإصلاحات الأمنية) — **جارٍ التنفيذ**.
3. تصميم نموذج بيانات المؤسسات (Multi-tenancy schema) للمراجعة قبل الـMigration.
